## Context

Clawdmeter's board-porting model (`docs/porting/adding-a-board.md`) assumes two invariants that hold across all seven existing ports:

1. **The display is QSPI or plain SPI**, driven by GFX Library for Arduino (`Arduino_CO5300`, `Arduino_SH8601`, `Arduino_ST77916`, `Arduino_ST7789`, etc.).
2. **BLE is provided by the same MCU running the app**, via NimBLE-Arduino talking directly to that MCU's own radio (S3 or C6).

The Waveshare ESP32-P4-WIFI6-Touch-LCD-5 breaks both invariants: its panel is MIPI-DSI (720×1280, 5", 2-lane), and its SoC (ESP32-P4) has no radio at all — Wi-Fi 6 / BLE 5 comes from an onboard ESP32-C6-MINI module wired to the P4 over SDIO, which is Espressif's "ESP-Hosted" pattern (the C6 runs its own firmware; the P4 talks to it as a remote radio, not a peripheral it drives directly).

Waveshare's own docs for this exact SKU (docs.waveshare.com/ESP32-P4-WIFI6-Touch-LCD-5) recommend ESP-IDF and describe Arduino support as "currently limited." Every other project constraint (pioarduino platform pin, GFX Library, LVGL-via-Arduino, NimBLE-Arduino) assumes the Arduino framework works cleanly, so this design has to establish whether that assumption survives contact with this board before anything else.

**Correction (2026-07-23, from Waveshare's official BSP source, not a guess):** the display driver is **HX8394**, not EK79007 — the EK79007 assumption below was inferred from a *different*, unofficial community repo for a related P4 board and turned out to be wrong for this SKU. Waveshare's own `waveshareteam/ESP32-P4-WIFI6-Touch-LCD-5` repo (`examples/esp-idf/08_lvgl_demo_v9/.../esp32_p4_wifi6_touch_lcd_5.c`) confirms: display panel is HX8394 over MIPI-DSI (`esp_lcd_hx8394`, `HX8394_720_1280_PANEL_30HZ_DPI_CONFIG`), touch is **GT911** over I2C (`esp_lcd_touch_new_i2c_gt911`, probing primary then backup address) — I2C on GPIO7 (SDA) / GPIO8 (SCL), `LCD_BACKLIGHT` = GPIO26 (LEDC PWM), `LCD_RST` = GPIO27, touch reset/interrupt pins are `GPIO_NUM_NC` (not wired — touch is I2C-only, no dedicated INT/RST lines broken out on this board). See "Spike Findings" below — this repo contains **zero Arduino examples and zero BLE/NimBLE/ESP-Hosted examples of any kind**, only ESP-IDF-native C examples.

## Goals / Non-Goals

**Goals:**
- Establish, before writing board-specific code, whether this board can be brought up at all inside this project's existing Arduino/PlatformIO toolchain (vs. needing a fundamentally different build path).
- If feasible, land a `waveshare_p4_touch_lcd_5` board port that follows the existing HAL contract exactly like every other board — `main.cpp`/`ui.cpp`/`splash.cpp` stay untouched.
- Get the shared UI rendering correctly on a 720×1280 portrait panel and touch input working, with BOOT-button-only input (no PWR/secondary button, no rotation, no battery %).
- Get BLE working end-to-end with the existing daemon/GATT contract, however that turns out to be wired underneath (directly through NimBLE-Arduino if ESP-Hosted is transparent to it, or through whatever alternate path the spike determines).

**Non-Goals:**
- Camera (OV5647 / MIPI-CSI), audio codec (ES8311/ES7210), dual-mic array, IMU/rotation, battery percentage reporting. None of these are wired up in this change, matching the project's existing posture of shipping "not verified yet" as an explicit no-op rather than guessing.
- Rewriting `hal/` to add a first-class "companion radio" abstraction speculatively. If the spike shows ESP-Hosted is transparent to NimBLE-Arduino, no such abstraction is needed at all — bring-up is just another `board_init.cpp` responsibility, like IO-expander release on AMOLED-1.8.

## Decisions

### 1. Sequence a feasibility spike as its own phase, before board.h/HAL work
Every prior port started by copying `boards/template/` and filling in pins, because the SoC/display/radio stack was already proven (same MCU family, GFX-supported panel, native NimBLE). Here, three separate unknowns each independently gate whether the normal port process even applies:
- Does the pinned pioarduino/Arduino-ESP32 core (or a newer release) support ESP32-P4 with MIPI-DSI at all?
- Does GFX Library for Arduino have a MIPI-DSI panel class, or does driving this panel require calling ESP-IDF's `esp_lcd_dsi`/`esp_lcd_panel` APIs directly (bypassing GFX Library, and likely bypassing LVGL's existing flush-callback wiring pattern too)?
- Does NimBLE-Arduino work unmodified against ESP-Hosted's SDIO-tunneled BLE controller, or does BLE on this board need a different stack/initialization path?

**Alternative considered**: skip the spike and start with `board.h` like every other port, treating unknowns as normal per-board gotchas to discover during bring-up (the project's usual style, per CLAUDE.md's "verified empirically" gotchas). Rejected here specifically because the *combination* of "docs say Arduino support is limited" + "no existing port has ever used this display interface" + "no existing port has ever used a companion-chip radio" means a failure isn't a small per-board fix, it can invalidate the chosen framework/library stack for the whole port. Finding that out after board.h/display.cpp/touch.cpp are already written wastes far more effort than a dedicated first pass answering exactly these three questions on hardware.

### 2. Prefer GFX Library + LVGL + NimBLE-Arduino unmodified if the spike allows it; fall back to ESP-IDF calls only where forced
If MIPI-DSI support exists in GFX Library (or a compatible Arduino-friendly wrapper such as `esp-arduino-libs/ESP32_Display_Panel`) and ESP-Hosted's BLE transport is transparent to NimBLE-Arduino, this port looks exactly like every other one architecturally: a `boards/waveshare_p4_touch_lcd_5/` folder implementing the same five HAL headers, zero shared-code changes. **Spike findings below show this optimistic case does not hold today** — recorded here to preserve the reasoning for why it was tried first.

**Alternative considered**: write straight to ESP-IDF's native `esp_lcd_panel_ops`/DSI APIs from the start, sidestepping GFX Library entirely, on the theory that P4 support in these Arduino wrapper libraries is newer and less battle-tested. Rejected as the default because it would mean this board's `display_hal_draw_bitmap` implementation looks nothing like any other board's, increasing long-term maintenance cost, and because the spike can cheaply determine whether the wrapper libraries actually work before committing either way. This remains the fallback if the spike shows the wrapper libraries don't work.

### 3. Board owns companion-radio bring-up the same way it owns IO-expander bring-up
If ESP-Hosted's BLE path is transparent to NimBLE-Arduino (decision #2's optimistic case), bringing up the ESP32-C6-MINI is just another `board_init()` responsibility — analogous to how AMOLED-1.8's `board_init.cpp` releases the XCA9554 IO expander before `display_hal_init()`. `main.cpp`/`ble.cpp` don't need to know a companion chip exists at all.

**Alternative considered**: introduce a new `radio_hal.h` alongside the existing five HAL headers, so any future companion-radio board has an explicit contract. Rejected for *this* change: with exactly one board needing this, adding a HAL header for it is the abstraction-before-second-use pattern the project's HAL docs explicitly warn against (`docs/porting/capability-flags.md`'s stance is a `BoardCaps` field or per-board file over new abstractions). If a second companion-radio board shows up later, extracting a `radio_hal.h` at that point costs little and will be informed by two real implementations instead of one guess.

### 4. No battery reporting in this change; power_hal returns a fixed "no battery" stub
Waveshare's docs disclose a bare MX1.25 3.7V connector with no PMU or fuel-gauge chip named. Rather than guess at an ADC pin/divider that may not exist, `power_hal_battery_pct()`/`power_hal_is_charging()` return the "no battery" values the shared UI already knows how to render (the battery icon logic already handles boards without a PMU — none of the two-button-only boards assume a battery is always present). Real battery support, if the hardware has any path to it, is a follow-up once someone has the board in hand to probe.

## Risks / Trade-offs

- **[Risk] Waveshare's own docs say Arduino support for this SKU is "currently limited," which could mean MIPI-DSI + Arduino is not viable at all on P4 today.** → Mitigation: the spike (task 1) answers this before any board-specific code is written; if Arduino is a dead end, the honest output of this change is a documented "not currently portable without an ESP-IDF-native display/BLE path" conclusion rather than a half-working port, and the OpenSpec change can be re-scoped or closed at that checkpoint instead of continuing sunk-cost work.
- **[Risk — resolved] The display/touch chips were initially guessed as EK79007/GT911 from an unofficial community repo for a different board.** → Resolved by reading Waveshare's own official BSP source for this exact SKU: display is **HX8394**, touch is **GT911** (the touch guess happened to be right; the display guess was not). No further probing needed for chip identity — the remaining risk is whether a working *Arduino-framework* driver exists for HX8394-over-DSI, which the spike findings below answer separately.
- **[Risk] If ESP-Hosted's BLE transport is NOT transparent to NimBLE-Arduino, this could force changes to shared `firmware/src/ble.cpp`, breaking the project's "zero `#ifdef BOARD_*` in shared code" rule.** → Mitigation: decision #3 keeps the abstraction board-local as long as possible; if the transparency assumption fails, the spike surfaces it early and the resulting shared-code design gets its own explicit sign-off (likely worth a follow-up change) rather than being silently bolted onto this one.
- **[Risk] 720×1280 portrait at 5" is a much higher pixel count (921,600px) than any existing port (480×480 = 230,400px is the current largest), with the same or less PSRAM headroom question mark.** → Mitigation: task list includes explicitly checking LVGL buffer / partial-flush strategy sizing against this board's real PSRAM (32MB in-package, same nominal size as the S3 boards, but P4's memory architecture differs enough from S3 that it's a check, not an assumption).
- **[Trade-off] No battery %, no camera, no audio in this change.** → Accepted: matches the project's existing pattern of shipping partial hardware support explicitly (e.g. the 2.06 board's un-wired chime path) rather than blocking the whole port on unrelated subsystems.

## Open Questions

- Does this board have any usable battery-percentage signal at all (raw ADC pin, I2C fuel gauge not mentioned in docs but present on the PCB), discoverable only by inspecting the physical board? (Deferred — out of scope, but worth a note for whoever picks this up next)

## Spike Findings

### Round 1 — desk research only (2026-07-23, no board connected)

Initial desk research (README summaries for GFX Library, NimBLE-Arduino, and arduino-esp32's own issue tracker) suggested both display and BLE were categorically blocked upstream. **This turned out to be too pessimistic and partly wrong** — README-level summaries don't reflect what the actual installed toolchain and library source can do. Superseded by Round 2 below; kept here only as a record of what looked true before hardware arrived.

### Round 2 — hardware connected, live build/flash verification (2026-07-23)

The user connected the real board mid-session (`esptool` confirms genuine ESP32-P4 rev v1.3, MAC `80:f1:b2:d1:c3:da`). Real `pio run`/`pio run -t upload` attempts against this exact hardware, using this project's already-pinned toolchain (`pioarduino/platform-espressif32` `55.03.38-1`, `arduino-esp32` core 3.3.8, bundled ESP-IDF 5.5.4), replaced the desk-research guesses with verified results. The picture is **split, not uniformly blocked**:

**Display: portable, moderate effort.** The installed `framework-arduinoespressif32-libs` for `esp32p4` already ships the real `esp_lcd_mipi_dsi.h`/`esp_lcd_panel_ops.h` headers (ESP-IDF 5.5.4's DSI driver, not a stub) — a minimal sketch calling `esp_lcd_new_dsi_bus()` directly built and linked cleanly. GFX Library still has no DSI wrapper class (confirmed), but that only rules out the convenience library, not the underlying capability. Went further: pulled Waveshare's own official `esp_lcd_hx8394` driver source (`waveshareteam/ESP32-P4-WIFI6-Touch-LCD-5`, `examples/esp-idf/08_lvgl_demo_v9/.../components/esp_lcd_hx8394/`) and vendored it directly into a throwaway board folder (not via PlatformIO's component manager — see below for why that path doesn't work). After two trivial fixes (drop one dead `#include "i2c_bus.h"` that's only referenced from commented-out example code in the vendor's own file; hand-define three cosmetic `ESP_LCD_HX8394_VER_*` version macros the component manager would normally auto-generate), **it compiled, linked, and flashed successfully to the real board** under `framework = arduino`. This validates decision #2's fallback for the display half: vendor the official driver source directly (same "avoid a problematic external dependency by vendoring a small reader" pattern this project already uses for touch controllers on AMOLED-1.8, just applied to a bigger driver file) rather than trying to pull it as a managed IDF component.
- Touch (GT911) wasn't build-tested this session, but is a plain I2C controller — same category of risk as any other board's touch controller, not a framework-level blocker.
- Full visual bring-up (actual pixels on the panel, not just link success) still needs the real init/reset/backlight sequence from Waveshare's BSP (`bsp_display_new()`'s DSI-PHY-LDO-power-on → dsi-bus → panel-io → panel-init chain) — that's normal task-3-level work, not a feasibility question.

**BLE: not portable today, and this is the real blocker.** Three independent lines of evidence, not just one:
1. A live build of this project's exact BLE dependency, `h2zero/NimBLE-Arduino` (PlatformIO resolved `^2.1.1` to the current latest, 2.5.0), against the real P4 target fails with genuine compiler errors inside NimBLE-Arduino's own FreeRTOS porting layer (`nimble_npl_os.h`'s `ble_npl_hw_set_isr` has a function-pointer/`uint32_t` signature mismatch against its own `npl_freertos.h` declaration; `uxGetCriticalNestingDepth` is undeclared) — this is upstream-library-internal, not anything fixable from a board's `board_init.cpp`.
2. NimBLE-Arduino's own maintainer (h2zero) confirmed this directly, on the record, in a closed upstream issue (h2zero/NimBLE-Arduino#906): *"This repo cannot support [ESP32-P4] due to dependencies and conflicts in the Arduino core. You will need to use esp-nimble-cpp and esp-idf to support this board."* That issue's last comment (2026, unresolved) notes even the latest release "still gives build failure with ESP32-P4 and Arduino Core 3.x."
3. The maintainer-recommended fallback — `h2zero/esp-nimble-cpp` (the ESP-IDF-native sibling library) — has its own currently-open failure mode reported independently by a different developer (h2zero/esp-nimble-cpp#377) targeting this exact board family: a `syscfg/syscfg.h: No such file or directory` error, reproduced under **both** `framework = arduino` and `framework = espidf` in PlatformIO. Root cause, confirmed by my own component-manager test here: **PlatformIO's `framework = arduino` build does not process `idf_component.yml` at all** — placing one at the project root or in `src/` is silently ignored (no fetch attempt, no error, just absent from the dependency graph). `esp-nimble-cpp`'s ESP32-P4 support depends on transitively pulling `espressif/esp_hosted` and `espressif/esp_wifi_remote` as managed components declared in *its own* `idf_component.yml` — exactly the mechanism that doesn't fire under `framework = arduino`. Switching to `framework = espidf` does invoke the component manager, but the other developer hit the identical `syscfg.h` error there too, meaning the bug isn't the framework choice, it's in how PlatformIO's component manager resolves this specific dependency graph for the `esp32p4` target today.

The asymmetry matters: the display fix worked because vendoring one self-contained ~500-line driver file sidesteps the component manager entirely. BLE's dependency chain (`esp-nimble-cpp` → `esp_hosted` (a full SDIO slave-host transport protocol implementation, not a header) → `esp_wifi_remote`) is not realistically hand-vendorable the same way — it's a real device-driver stack, not a single panel-init file. **No one — not Waveshare's own official demo repo (zero BLE examples in any framework), not this session's testing, not either of the two upstream bug reports found — has a working BLE-on-this-board example today, under PlatformIO, in any framework.**

**Revised net result:** this is no longer a uniform "wait for upstream" or "go full ESP-IDF" call — it's specifically a **BLE blocker**, with the display/touch side now de-risked to roughly the same effort level as any other new-panel-type board port (vendor a driver, wire up the HAL, tune the bring-up sequence on hardware). See the options below for how to proceed given that split.

### Options given the revised (display-OK, BLE-blocked) picture

1. **Ship display+touch now, defer BLE.** Port the display/touch/input/power/IMU HAL exactly as scoped, using the vendored-driver approach validated above. Leave BLE as an explicit stub (`ble.cpp` compiles to a no-op on this board) until the upstream BLE blocker clears. Downside: without BLE this board can't actually show live usage data — the core purpose of the product — so this only makes sense as a staged/visible-progress delivery, not a finished port.
2. **Attempt to vendor the full BLE-over-hosted stack by hand** (esp_hosted's SDIO transport + esp_wifi_remote + esp-nimble-cpp, all as raw vendored source bypassing PlatformIO's component manager the same way the display driver was vendored). Unproven, substantially larger than the display vendoring effort, and might hit its own undiscovered bugs given no one has gotten this far yet on this exact board.
3. **Try a raw `idf.py`-based build for this one board** (bypassing PlatformIO entirely, since PlatformIO's component manager is where the confirmed bug lives, not ESP-IDF itself) — closest to what Waveshare's own examples do, but means this board can't live in the shared `firmware/platformio.ini` alongside every other board; it'd need its own build pipeline.
4. **Wait for upstream fixes** to either NimBLE-Arduino's P4 FreeRTOS port or PlatformIO's component-manager handling of `esp32p4` — both are known, tracked, currently-open problems, not undiscovered ones, so there's a real (if unpredictable) chance they resolve on their own.
5. **Swap to a different, proven rectangular board** not affected by any of this (e.g. an ESP32-S3-based Waveshare rectangular touch LCD, same family as the already-working `waveshare_lcd_154` port).

### Resolution: Option 1, implemented and verified on hardware (2026-07-23)

Display + touch are fully working, confirmed live on the actual board: splash animation renders correctly, tapping the screen navigates to the pairing-hint screen (BLE deliberately stubbed via `ble_stub.cpp`, so the UI correctly shows "not paired" rather than usage data), text at the existing "large" breakpoint's font sizes is fully readable with no clipping despite the panel being far larger than any prior board.

Two real bugs were found and fixed along the way, beyond what the spike anticipated:

1. **DPI panel async/DMA2D race** (board-local, `display.cpp`): `esp_lcd_panel_draw_bitmap()`'s DMA2D path queues a copy and returns before it's done; LVGL believed the source buffer was free to reuse as soon as the call returned. Fixed by using the driver's synchronous CPU-copy path (`use_dma2d = false`) with a retry loop on its busy state instead.
2. **Null font-pointer bug in shared `ui.cpp`** (not board-specific): `compute_layout()`'s "large" and "compact" breakpoints never set `L.pct_font`/`L.reset_font`, which `make_usage_panel()` passes straight to `lv_obj_set_style_text_font()`. Harmless on every Xtensa board shipped so far; hangs LVGL's renderer outright on ESP32-P4. Fixed in shared code (values matching what `ui_update()` already uses once real data arrives) — this benefits every board, not just this one, and was the actual root cause of what first looked like a P4-specific "large const array" issue before closer investigation.

A third, purely local bug: this specific GT911 unit's touch coordinate bytes are ordered high-byte-first, opposite of some published GT911 register maps — found by dumping raw register bytes against a known tap location, fixed in `touch.cpp`.

BLE remained deferred exactly as scoped in option 1 for one further session — `ble_stub.cpp` was a clean, permanent no-op substitute for shared `ble.cpp` in this board's `build_src_filter`, with zero changes to any other shared file. **This has since been superseded — see "BLE resolution" below; `ble_stub.cpp` no longer exists.**

### BLE resolution: a fourth option nobody had scoped — arduino-esp32's own bundled `BLE` library (2026-07-24)

Every option above assumed the only two BLE paths were `h2zero/NimBLE-Arduino` (confirmed broken on P4) and the ESP-IDF-native `esp-nimble-cpp` + `esp_hosted` + `esp_wifi_remote` stack (confirmed broken under PlatformIO's component manager for both frameworks). There turned out to be a third path neither option considered: **arduino-esp32 core's own bundled `BLE` library** (`#include <BLEDevice.h>`), a completely different, older-generation C++ wrapper shipped as a standard Arduino library inside the framework itself — not a `NimBLE-Arduino`-family project at all, just sharing similar-sounding class names.

This works because the *installed* `framework-arduinoespressif32-libs` package (the one this project already pins) ships with `CONFIG_ESP_HOSTED_ENABLE_BT_NIMBLE=1` baked into its sdkconfig and a precompiled `libbt.a` containing the full ESP-IDF-native NimBLE-over-ESP-Hosted stack — found by grepping the installed package directly, not by reading any docs. `h2zero/NimBLE-Arduino` fails because it vendors and compiles its *own* copy of the NimBLE source tree from scratch, and that copy has real bugs in its P4 FreeRTOS porting layer; the bundled `BLE` library instead just links against Espressif's own precompiled, already-P4-working stack. No hybrid `framework = espidf, arduino` mode was needed (that path was tested too, in parallel — it also works, and does invoke the component manager PlatformIO's `framework = arduino` mode skips, but hit its own `CONFIG_FREERTOS_HZ` mismatch and was abandoned once the simpler path proved to work first). No SDIO pin configuration was needed either — arduino-esp32's generic `esp32p4` board variant already defaults to the exact pins Waveshare's own schematic shows wired to the onboard ESP32-C6-MINI.

Verified end-to-end on hardware: the board advertises as "Clawdmeter", is discoverable via a real BLE scan (`bleak`), and — the definitive test — **paired successfully through the user's actual macOS Bluetooth settings**, the same real-world flow the host daemon relies on for every other board.

One real bug surfaced and cost a full crash-reboot-loop debugging pass (bisected with per-call `ESP_LOGE` markers, since `Serial.print` output proved unreliable on this board throughout — see CLAUDE.md's P4 section for the "why" and the general lesson): `BLEHIDDevice::manufacturer(String)` (the setter) dereferences `m_manufacturerCharacteristic`, a member that's *only* created by the no-arg `manufacturer()` getter — unlike every other HID setter used (`reportMap`/`pnp`/`hidInfo`/`setBatteryLevel`), whose backing characteristics are all pre-created in the constructor. Calling the setter without the getter first is a silent null-pointer dereference into `setValue()`. Fixed by calling `hid_dev->manufacturer();` once before `hid_dev->manufacturer("Anthropic");`.

The board-local `boards/waveshare_p4_touch_lcd_5/ble.cpp` reimplements shared `ble.cpp`'s full contract (custom data service, single-owner bond lock, HID keyboard, Windows supervision-timeout pushback) against this different API — see that file's header comment for the complete list of API differences and how each was adapted. Shared `ble.cpp` and every other board remain completely untouched.
